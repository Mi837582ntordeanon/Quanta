# AGENTS.md — Quanta

Проект: Quanta (Q.W.A.N.T.A., персонаж «Кванта») — локальный Windows-ассистент.
Python-сервер на stdlib (127.0.0.1), UI на vanilla JS, Ollama и OpenAI-совместимые API,
tool-calling, управление ПК, MCP-клиент, голос, Minecraft, память.

## Как работать

* Первым делом читай docs/PROGRESS.md. Если его нет, создай (см. этап 0 в docs/STAGES.md).
* Этапы лежат в docs/STAGES.md. Берёшь ТОЛЬКО следующий невыполненный этап, остальные не трогаешь.
* Один шаг = рабочее состояние: тесты зелёные, ничего не сломано посередине.
* Если чувствуешь, что лимит близок: остановись на чистой границе, обнови docs/PROGRESS.md
и docs/IMPLEMENTATION\_REPORT.md, потом остановись. Лучше честно «частично», чем полусломанное.

## Правила

* Не ломай поведение. Сначала характеризационные тесты, потом рефакторинг.
* Не пиши «сделано» без запущенной проверки. Заглушки и TODO вместо реализации запрещены.
* Windows-части, которые не можешь запустить, помечай «не проверено на Windows»
и давай шаги ручной проверки.
* Новые зависимости только с обоснованием и точно закреплённой версией. Предпочитай stdlib.
* Неоднозначность решай консервативно и записывай решение в отчёт.
* Не вводи сроки и даты в код, документы и отчёты.

## Прозрачность

Перед каждым шагом 1–2 строки: что делаешь и зачем.
После шага: изменённые файлы, запущенные команды и их фактический результат, что не получилось.

## Сдача этапа

После каждого задания (этапа или его части) работа считается сданной только после проверок,
коммита, отправки ветки и сборки архива для ревью.

1. Запусти проверки из этого файла. Перед коммитом покажи полный вывод `git status --short`.
   Добавляй файлы в индекс только явными путями; не добавляй `api_secrets.json`, `data/`, трассы,
   `__pycache__/`, `.env` и локальные диагностические файлы.
2. Создай коммит и отправь текущую ветку. Архив собирается только из коммита через `git archive`;
   незакоммиченные изменения в него не попадают, поэтому коммит обязателен до сборки.
3. Если доступен `gh`, найди GitHub Actions run для этого коммита и дождись завершения. Если `gh`
   недоступен или run не найден, укажи в сдаче точную фразу `CI не проверен`.
4. Запусти `tools/make_review_archive.ps1 -Stage <название этапа>`.
5. В последнем сообщении перечисли файлы из `review/`, которые нужно загрузить на проверку,
   и укажи коммит, число тестов и результат CI.

## Если одна ошибка повторилась дважды

Сделай короткий разбор причины и добавь правило сюда.

* Разбор: при пакетном обновлении отчёта дважды смешал `bytes` и `str` в Python. Перед записью текстовых файлов проверяй типы, наличие всех маркеров и результат замен на копии данных; записывай только после успешной предварительной проверки.
* Разбор: при подготовке переноса методов `Toolbox` дважды использовал неполную ручную карту модулей (`undo_action` и методы Minecraft не попали в группу). До генерации или записи модулей сравнивай полный список методов по AST и все зарегистрированные обработчики с разбиением по доменам; останавливайся при любом пропуске.
* Разбор: при генерации mixin-модулей дважды ошибся в отступах существующих методов и новых декораторов. Сохраняй исходный отступ тела метода, размещай `@tool` на уровне декоратора метода и компилируй все кандидаты до записи файлов.
* Разбор: при извлечении ветки AST дважды сравнил `ast.unparse()` с точной строкой; нормализация Python добавила скобки. Для выбора узлов проверяй типы и поля AST, а не форматированный текст.
